# 0020. Identity and session management: Keycloak + Spring Security + Redis-backed Spring Session

Date: 2026-08-07

Status: Accepted

## Context

MVP 0.6 ("Identity & session") deliberately reverses ADR 0016's hand-rolled authentication and CLAUDE.md's "no Redis" constraint — the same kind of planned reversal "no authentication" underwent for MVP 0.5. This was planned as two issues, #85 (Spring Security + Keycloak + Redis-backed Spring Session, backend-only) and #86 (cookie-based WebSocket handshake + frontend adaptation), but implementation revealed they aren't independently shippable: the moment `POST /login`/`AuthService` are deleted (#85's explicit scope), the frontend's `Login.tsx` and `App.tsx` break immediately (dead fetch target, and `App.tsx` would fail to even compile once `Login.tsx` is gone in #86) — leaving the app completely unusable between the two PRs, violating "keep the application runnable at every stage." Both are implemented together here, mirroring the #34/#22 precedent from MVP 0.4's retro.

## Decision

* **Keycloak via `oauth2Login` (authorization code grant), replacing `AuthService`/`POST /login` entirely.** `AuthService`, `AuthProperties`, `DemoUser`, `LoginController`, `LoginRequest`/`LoginResponse`, and `CorsConfig` (dead code once `POST /login` — the only thing needing CORS — is gone) are all deleted. Demo users (`trader1`/`trader2`) move into Keycloak's realm config (`keycloak/sdp-realm.json`, issue #83) instead of `application.yml`.
* **Redirect-based BFF pattern, not a token visible to the SPA.** The backend is the (confidential) OAuth2 client. An unauthenticated request to a protected path gets Spring Security's default entry point response (a redirect toward Keycloak's hosted login page); after login, Keycloak redirects back to the backend's callback (`/login/oauth2/code/keycloak`), and `oauth2Login`'s success handler redirects the browser again — to `app.frontend-origin` (reusing the same property from ADR 0016/issue #84's env-var convention) rather than Spring Security's default (the originally-requested backend URL), since the flow is a top-level navigation initiated from the frontend, not a request to a backend page worth returning to.
* **Redis-backed Spring Session (`@EnableRedisWebSession`) carries identity to the WebSocket handshake.** Once logged in, the browser holds a session cookie for the `localhost` domain — cookies aren't port-scoped, so this cookie rides along automatically on the WS upgrade request to the backend's port, even though the page is served from the frontend's different port. `SecurityConfig` protects `/ws` with `.pathMatchers("/ws").authenticated()`; `SdpWebSocketHandler` now resolves the username from `webSocketSession.getHandshakeInfo().getPrincipal()` instead of a query-param token — and can assume it's always present, since the security filter chain rejects unauthenticated upgrades before `handle()` is ever invoked. `Session` (ADR 0017) and `SymbolSubscription` ownership are **unaffected in shape** — only where `Session`'s username comes from changes. Spring Session (HTTP-level, Redis-backed, *does* survive across requests by design) and the app's own `Session` (WS-connection-level, ADR 0017, deliberately does *not* survive a reconnect) remain two different layers; this doesn't reopen ADR 0017's decision.
* **`@EnableRedisWebSession` is explicit, not property-triggered.** `spring-session-data-redis` (this version) ships no Spring Boot auto-configuration of its own for the reactive/WebSession case — only for the servlet/HttpSession one. `spring.session.store-type=redis` alone does nothing here; the annotation is required.
* **Realm roles (`trader`, `viewer`) exist but aren't enforced yet.** Both demo users can do everything at the WS layer, same as before — role-based authorization is deliberately out of scope for this issue, a future increment once there's a concrete reason to gate specific operations.
* **`LOGIN_SUCCESS` now fires from `oauth2Login`'s authentication success handler, and `LOGIN_ERROR` — not a reused `LOGIN_FAILURE` — from its failure handler (issue #87).** `AuditingAuthenticationSuccessHandler`/`AuditingAuthenticationFailureHandler` (`com.sdp.config`) wrap the framework's own `RedirectServerAuthenticationSuccessHandler`/`RedirectServerAuthenticationFailureHandler`, recording the audit event before delegating to the same redirect behavior `SecurityConfig` used inline before. Both record with a `null` session id, since no `Session` (ADR 0017) exists yet at this point in the flow — the same convention `AuthService.login()` used. This is a genuine, accepted narrowing: once Keycloak owns the credential check, the app never sees a raw "wrong password" event, only whether the OAuth2 callback itself succeeded or errored (consent denied, code exchange failed, token verification failed, etc.) — `LOGIN_ERROR` records that failure's message (truncated to fit `audit_events.detail`) against a fixed `"unknown"` username, since no username is observable at this point when the callback fails. Keycloak's own admin console/logs still cover failed password attempts. `SESSION_STARTED` is unaffected (still fires from `SdpWebSocketHandler`, just reading identity differently).

## Consequences

* This app now depends on three additional pieces of real infrastructure it didn't need before (Keycloak, Redis, and Spring Security itself) — a deliberate, planned increase in complexity for this milestone, not incidental scope creep.
* **Testing a raw `WebSocketHandler`'s authentication without a browser is hard**, since the real login flow requires an actual redirect + hosted-login-page form submission. `SdpWebSocketHandlerIT` authenticates its test WS connections by seeding a session directly into Redis (`ReactiveRedisSessionRepository`, setting the `"SPRING_SECURITY_CONTEXT"` attribute `WebSessionServerSecurityContextRepository` itself reads/writes) rather than driving a real browser through Keycloak — once a session with a valid `Authentication` exists, the WS handshake code doesn't care how it got there. The actual Keycloak authorization-code exchange is verified live (browser-driven), not by an automated JUnit test; automating a full OAuth2 browser flow inside a test suite was judged disproportionate for this project's scale.
* An unauthenticated WS upgrade attempt now fails via an HTTP redirect at the security-filter layer (a `302`, since that's `oauth2Login`'s default unauthenticated entry point) rather than a clean WS-level close — a real behavior change from ADR 0016's `webSocketSession.close()`. A browser's `WebSocket` API can't follow a redirect either way, so the client-visible outcome (handshake fails, `onopen` never fires) is the same; the frontend's `connect()` treats "closed without ever having opened" as "not authenticated, go log in."
* The frontend loses its custom `Login.tsx` form and the `token` prop threaded through every WebSocket-owning component (`Greeting`, `PriceGrid`, `ExecutionConfirmation`, `TradeBlotter`) — identity is now implicit (the session cookie), not something the app's own state holds or passes around.
* A future "view the audit trail" or role-enforcement feature can build on the realm roles already provisioned in `keycloak/sdp-realm.json`, without another identity redesign.
* **`KC_HOSTNAME` must be given as a full URL, not a bare hostname plus a separate port.** Keycloak 26 defaults to its "hostname v2" provider, which has no `hostname-port`/`hostname-strict` options — those are v1-only and are silently ignored (only a startup `WARNING` log, no hard failure). Setting `KC_HOSTNAME=localhost` with a separate `KC_HOSTNAME_PORT=8081` therefore does nothing to fix the port: v2 falls back to the container's actual internal port (`8080`) for the token issuer instead of the host-published one (`8081`), so the issuer minted for the browser and the issuer expected when the backend calls userinfo/jwks disagree, and every login fails with `[invalid_user_info_response] Token verification failed`. `docker-compose.yml` sets `KC_HOSTNAME: http://localhost:8081` (a full URL) instead — see that file's comment for the reasoning; this bit us once (found and fixed live while verifying issue #85/#86) and would bite again on any future Keycloak hostname reconfiguration.
* **Keycloak's realm-import format only accepts plaintext credential values**, which it hashes on import (`keycloak/sdp-realm.json`'s `credentials[].value`) — unlike `application.yml`'s pre-hashed `password-hash` fields under the old `AuthProperties` (ADR 0016). This is inherent to the bootstrap mechanism, not a regression in how secrets are normally handled here: these are dev/demo credentials committed to the repo either way, and Keycloak still stores them hashed at rest once imported.
* **A realm-import JSON that omits `sslRequired` defaults to `EXTERNAL`, not `NONE`** — a gap present in `keycloak/sdp-realm.json` since this issue and never noticed until MVP 0.7's retro, because `EXTERNAL` tolerates `localhost`/loopback/private-subnet traffic over plain HTTP and this project's traffic almost always looks like that. It broke visibly once a request came in over a path Keycloak didn't classify as local (surfaced as Keycloak's own "HTTPS required" error page, not an application-level error), which is easy to mistake for a TLS/proxy misconfiguration rather than a one-line realm setting. Fixed by adding `"sslRequired": "none"` to the realm, the correct explicit setting for a local-only dev/demo deployment with no TLS anywhere in the stack.
