# 0006. MVP 0.6 — Identity & session

Date: 2026-08-10

Milestone: [MVP 0.6 – Identity & session](../roadmap.md)

## What shipped

All 5 issues in the MVP 0.6 milestone, across 4 merged PRs (#85 and #86 were bundled into one PR — see Deviations):

- **Docker Compose: Redis + Keycloak containers** (#83, PR #96): `redis:7-alpine` and `keycloak:26.7.1` added alongside the existing stack, both pinned by digest. Keycloak bootstraps its `sdp` realm from `keycloak/sdp-realm.json` on import, with `trader`/`viewer` roles and the same `trader1`/`trader2` demo users the old `application.yml`-based auth used. Infrastructure only — the app's hand-rolled auth kept working unaffected.
- **Externalize `application.yml` config via env vars** (#84, PR #97): `${ENV_VAR:default}` placeholders for R2DBC and `app.frontend-origin`, establishing the pattern the rest of this milestone (and MVP 0.7's RabbitMQ config) would follow.
- **Spring Security + Keycloak (`oauth2Login`) with Redis-backed Spring Session** (#85) **and cookie-based WebSocket handshake + frontend adaptation** (#86), PR #98: the hand-rolled `POST /login`/`AuthService` (ADR 0016) is replaced entirely by Spring Security's `oauth2Login` against Keycloak (authorization code grant); Spring Session is backed by Redis (`@EnableRedisWebSession`) so identity survives a backend restart; `SdpWebSocketHandler` resolves the session's username from the authenticated WebSocket handshake principal instead of a query-param token, and `/ws` requires authentication before `handle()` is ever invoked. `Login.tsx` and the `token` prop threaded through every WS-owning frontend component are gone — identity is now implicit (the session cookie). ADR 0020, superseding ADR 0016.
- **Audit semantics for the Keycloak login flow + doc updates** (#87, PR #99): `LOGIN_SUCCESS`/`LOGIN_ERROR` (not a reused `LOGIN_FAILURE`) now fire from `AuditingAuthenticationSuccessHandler`/`AuditingAuthenticationFailureHandler`, wrapping `oauth2Login`'s success/failure handling. `LOGIN_ERROR` is a deliberate, documented narrowing — Keycloak owns the credential check now, so a raw "wrong password" attempt is no longer observable at this app's boundary at all.

## Verified

- Backend: `./gradlew clean test integrationTest` from a clean `main`, no cache — 31 unit + 13 integration tests, all passing, including real Postgres (`AuditEventRepositoryIT`) and Redis (`RedisIntegrationTest`, via `SdpWebSocketHandlerIT`) round trips.
- Frontend: `npm run test:unit` (25 tests) and `npm run test:integration` (1 test) from a clean `main` — all passing.
- Live, through **both** documented run paths:
  - **Docker Compose**: real browser login through Keycloak's hosted page (`trader1`/`trader1pass`), redirected back to the frontend with a working session; queried `audit_events` directly via `psql` and found a `LOGIN_SUCCESS` row for `trader1` with a null session id; hit the OAuth2 callback with a deliberately invalid `code`/`state` and confirmed a `LOGIN_ERROR` row (`username="unknown"`, detail `[authorization_request_not_found]`) plus the expected `/login?error` redirect.
  - **Without Docker** (`./gradlew bootRun` + `npm run dev`, infra via `docker compose up -d postgres redis keycloak`): confirmed the backend starts and a login redirect succeeds (`302` + `Set-Cookie: SESSION=...`) with all three infra containers up. The interactive browser click-through for this path (as opposed to the `curl`-based redirect/cookie check) couldn't be completed this session — the Claude-in-Chrome browser extension disconnected mid-verification and didn't reconnect. Backend behavior for this path is otherwise identical to the already browser-verified Docker Compose path (same Keycloak instance, same cookie mechanism), so the risk this leaves unverified is low, but it's a genuine gap in this retro's own verification rather than something to paper over.

## Bugs and gotchas found

- **`KC_HOSTNAME` must be a full URL, not a bare hostname plus a separate port — found and fixed live while verifying #85/#86 (PR #98).** Keycloak 26 defaults to its "hostname v2" provider, which has no `hostname-port`/`hostname-strict` options; setting them (as `docker-compose.yml` originally did) is silently ignored (a startup `WARNING`, not a hard failure), so the token issuer fell back to the container's internal port (`8080`) instead of the host-published one (`8081`) — every login failed with `[invalid_user_info_response] Token verification failed`. Root-caused by reading Keycloak's *own* server log (`type="USER_INFO_REQUEST_ERROR", reason="Invalid token issuer..."`), not the Spring-side stack trace, which only showed the generic wrapper. Fixed to `KC_HOSTNAME: http://localhost:8081` (a full URL); documented in [ADR 0020](../decisions/0020-keycloak-oauth2-redis-session.md)'s Consequences.
- **README's "Without Docker" instructions broke without anyone noticing — found during this retro, not during #83/#85/#86's own PRs.** `README.md` only ever said `docker compose up -d postgres` for the native run path; once #85/#86 made Redis and Keycloak hard requirements for login, that instruction silently stopped being sufficient. The backend itself still starts fine (nothing calls out to either service eagerly at startup — this app deliberately avoids the `issuer-uri` shortcut that would trigger eager OIDC discovery, see ADR 0020), but the very first login attempt 500s (`/oauth2/authorization/keycloak` can't persist the OAuth2 authorization request to a session without Redis reachable). Reproduced deliberately (only Postgres up, confirmed the 500, then confirmed `docker compose up -d postgres redis keycloak` fixes it) before fixing `README.md`. This is exactly the class of gap this skill's step 2 exists to catch — it slipped through every individual PR because each one was verified against whichever run path was fastest to iterate on (per each PR's own "Testing" notes, #98 and #99 only mention the Docker Compose path), not cross-checked against the other documented path until all of MVP 0.6 was merged together.
- Keycloak's realm-import format only accepts plaintext credential values (it hashes them on import), unlike `application.yml`'s pre-hashed fields under the old `AuthProperties` — inherent to the bootstrap mechanism, not a secrets-handling regression, since these are dev/demo credentials either way. Noted in ADR 0020.

## Deviations from plan

- **#85 and #86 were bundled into a single PR (#98) instead of shipped separately**, as originally scoped. Implementation revealed they weren't independently shippable: deleting `AuthService`/`POST /login` (#85's scope) breaks the frontend's `Login.tsx` and `App.tsx` immediately, leaving the app unusable between the two PRs — a direct violation of "keep the application runnable at every stage." Documented in [ADR 0020](../decisions/0020-keycloak-oauth2-redis-session.md)'s Context, mirroring the #34/#22 precedent from MVP 0.4's retro.
- No other structural deviations from the roadmap.

## New skill candidates surfaced

- **`ship-issue`'s live-verification step should explicitly re-check every README-documented run path whenever a change adds or changes required infrastructure**, not just whichever path is fastest to iterate on locally. Every individual MVP 0.6 PR's "Testing" notes show verification against the Docker Compose path only (except #97, which happened to check both) — the native "Without Docker" path's breakage went undetected for the whole milestone precisely because no single issue's own scope was "update the without-Docker instructions," so nobody was prompted to check it. This is the same class of gap `milestone-retro`'s own step 2 exists to catch, but catching it only at milestone-close means a broken README ships and stays broken for the milestone's full duration instead of one PR's worth of time. Concretely: when a PR's diff touches `docker-compose.yml`'s service list, `application.yml`'s required config, or anything else load-bearing for booting the app, `ship-issue` should prompt re-verifying the *other* documented run path too, not just the one the change was developed against.
