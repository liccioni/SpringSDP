# 0012. MVP 1.2 — Per-session trade delivery

Date: 2026-08-26

Milestone: [MVP 1.2 – Per-session trade delivery](../roadmap.md)

## What shipped

The milestone's only issue, #152 (the gateway's `EventBus` broadcast `TRADE_CREATED`/`TRADE_REJECTED` to every connected session regardless of who submitted the trade), closed via one PR (#158), after a design process that went through three iterations before landing on the shipped shape:

- **Iteration 1 (PR #157, discarded before this milestone started):** bolt a `submittedBy` identity field onto the broadcast and filter `EventBus` delivery by it. Rejected as the wrong mechanism — it re-invented per-connection targeting the codebase already had via the correlated request/reply pattern (`TRADE_PENDING`/`TRADE_CANCELLED`/`TRADE_HISTORY`).
- **Iteration 2 (considered, not implemented):** make `TRADE_CREATED`/`TRADE_REJECTED` purely correlated replies, deleting the broadcast entirely. Broke down on closer reading of the frontend: `TradeBlotter.tsx`'s live cross-user refresh (another trader's execution appearing in the blotter without a manual reload) is legitimate desired behavior, not the bug — a pure "submitter only" model would have silently regressed it.
- **Iteration 3 (shipped):** two independent delivery mechanisms for two genuinely different concerns.
  1. **Submitter acknowledgment** — `CONFIRM_TRADE` now gets a real correlated `TRADE_CREATED` reply (was fire-and-forget), delivered via the connection's own `directMessages` sink regardless of any subscription state. `CREATE_TRADE`'s rejection reply now carries the real `TradeRejected` payload (was `null`) over the same channel, and never broadcasts — a rejected trade is never persisted, so there's nothing for anyone else to see.
  2. **Blotter live-refresh** — a new `BlotterSubscription` (`gateway/src/main/java/com/sdp/trade/BlotterSubscription.java`), structurally identical in spirit to `SymbolSubscription`/`PRICE_TICK` (ADR 0013) but a plain subscribed/unsubscribed flag rather than per-symbol filtering. New `SUBSCRIBE_BLOTTER`/`UNSUBSCRIBE_BLOTTER` message types, sent by `TradeBlotter.tsx` on mount/unmount. The pre-existing `trade-created` RabbitMQ fanout and gateway's relay onto `EventBus` are kept unchanged — only the downstream visibility is now gated by the subscription.
  3. `tradeRejectedConsumer`, the `trade-rejected` fanout exchange, and the gateway-local `TradeRejected` `DomainEvent` class are deleted entirely — nothing publishes to that exchange anymore.
- **[ADR 0028](../decisions/0028-scoped-trade-delivery.md)** records the design and explicitly supersedes the specific delivery claims in ADR 0018 and ADR 0022 (their `Status:` lines now note this rather than being rewritten wholesale — both ADRs' other content, the two-step workflow and the service topology itself, still holds).
- A related idea raised in the same design conversation — expanding price-tick symbols from 3 to 10-20 with a default-subscribed subset — was deliberately scoped out rather than bundled in, per CLAUDE.md's "small, working iterations" philosophy. Captured as unscheduled backlog issue [#159](https://github.com/liccioni/SpringSDP/issues/159) with the design constraints already agreed.

## Verified

- Backend, from a clean `main` (fresh pull, `./gradlew clean test integrationTest`): `gateway` — 37 unit + 20 integration (retro 0011's baseline was 38 unit/19 integration; net change reflects one deleted unit test for the removed `tradeRejectedConsumer` bean, one deleted and one renamed integration test for the removed broadcast path, and three new regression tests). `trading-service` — 15 unit + 17 integration, same counts as retro 0011 (content changed, coverage didn't shrink). `market-data-service` — 3 unit, untouched by this milestone.
- Frontend: `npm run test:unit` (46 tests) and `npm run test:integration` (1 test), both green, no test changes needed for `PriceGrid`/`ExecutionConfirmation` — only `TradeBlotter.tsx` itself changed (to send `SUBSCRIBE_BLOTTER`/`UNSUBSCRIBE_BLOTTER`).
- Live, through **both** README run paths, each exercising the same two-connection scenario (two independent browser tabs, both authenticated as `trader1` via the real Keycloak login page, giving two separate WebSocket sessions per ADR 0017):
  1. `./startUpDocker.sh` (always rebuilds every image, avoiding retro 0001's stale-image trap): tab 1 submitted and confirmed a EUR/USD trade — its own pending-trade prompt resolved via the correlated reply, and tab 2 (which never sent anything) picked up the same trade live in its blotter via the `SUBSCRIBE_BLOTTER` broadcast, with no manual refresh.
  2. "Without Docker": `docker compose up -d postgres redis rabbitmq keycloak`, then `gateway`/`market-data-service`/`trading-service` via native `./gradlew bootRun`, frontend via native `npm run dev`. Login redirected to a stale, unrelated local process squatting on port 5173 (pre-existing local state, not something this session started) — worked around by navigating back to the frontend's actual port once authenticated, since the session cookie isn't port-scoped (per `docs/protocol.md`'s Authentication section). Same two-connection scenario repeated end to end with identical results against the fully native backend.
  3. No console errors in either browser tab on either path; gateway startup logs confirmed `tradeCreatedConsumer-in-0` bound and `tradeRejectedConsumer-in-0` absent in both.
- All four CI checks green on PR #158 (`detect`, `services (gateway)`, `services (market-data-service)`, `services (trading-service)`, `frontend`) before merge.

## Bugs and gotchas found

- **The design itself went through two rejected iterations before landing** (see "What shipped" above) — not a code bug, but worth recording as the actual lesson of this milestone: both rejected approaches skipped straight to a mechanism (an identity filter, then "make everything correlated") before confirming what the delivery requirements actually were. Reading how the frontend consumes `TRADE_CREATED` today (three separate consumers — `TradeBlotter`, `PriceGrid`, `ExecutionConfirmation` — with different needs) is what surfaced the real shape of the problem. Recorded in [ADR 0028](../decisions/0028-scoped-trade-delivery.md)'s Consequences section and in project memory (`feedback_flag_domain_decisions`).
- **A stale `spring.cloud.function.definition` entry for a deleted bean fails silently, not loudly** — new gotcha, added to [docs/testing.md](../testing.md)'s Known gotchas. Deleting `tradeRejectedConsumer()` before cleaning up its `application.yml` entries left the app in a state where tests and startup both looked completely clean, and only manually reading startup logs (not any test) revealed the binding was simply never created. A real typo in a function name would fail the identical, silent way.
- **Local port collision during live verification**: an unrelated, pre-existing local `node` process was already bound to port 5173 when starting the "Without Docker" path, so Vite's dev server started on 5174 instead, and the gateway's `app.frontend-origin` (defaulting to `:5173`) redirected post-login to the wrong server. Not a bug in this milestone's change — worked around by relying on the (already-documented) non-port-scoped session cookie to re-navigate to the actual dev server port. Not durable enough to warrant a docs change; noted here in case it recurs.

## Deviations from plan

- The milestone's own framing in `CLAUDE.md`/`roadmap.md` ("scope delivery to the submitting session only") undersold what actually shipped — see "What shipped" above. Both docs are corrected as part of this retro rather than left to silently drift, matching this project's now-recurring pattern (retro 0011 made the same kind of correction for MVP 1.1's "root-cause and fix" framing).
- `docs/roadmap.md`'s own MVP 1.2 bullet, written when the issue was filed, described the discarded PR #157 mechanism (`Trade`/`TradeRejected` carrying a submitter identity, filtered by identity) almost verbatim — a second, independent instance of the same drift this retro's step 5 exists to catch, now corrected in the same edit.
- The price-tick default-subset idea (#159) was raised, designed down to concrete constraints, and then deliberately not implemented in the same session — a real-time example of the scope discipline CLAUDE.md's Core philosophy asks for, rather than something caught after the fact.
