# 0005. MVP 0.5 — Dealer platform foundation

Date: 2026-08-07

Milestone: [MVP 0.5 – Dealer platform foundation](../roadmap.md)

## What shipped

All 5 issues in the MVP 0.5 milestone, across 6 merged PRs (one extra, milestone-less backlog issue was pulled forward — see Deviations):

- **Authentication** (#24, PR #74): `POST /login` — the app's first HTTP/REST endpoint — checks config-based demo users (BCrypt via the standalone `spring-security-crypto` artifact) and issues an opaque in-memory token; `SdpWebSocketHandler` rejects any WS connection with a missing or invalid token before any envelope is exchanged. ADR 0016.
- **Sessions** (#25, PR #75): a `Session` (id + username) is created once a connection's token validates, 1:1 with the connection's own lifetime — no reconnect continuity. Its first visible effect: a personalized `HELLO` ("Hello, trader1!") replacing the old static greeting. ADR 0017.
- **Extract subscription filtering out of `SdpWebSocketHandler`** (#69, PR #76): a pure refactor moving the handler's `Set<String>`/`isVisible` business logic into a new `SymbolSubscription` (`com.sdp.market`) — done ahead of #26 because #26's own issue body named this as its prerequisite.
- **Per-session market data subscriptions** (#26, PR #77): `Session` now owns a `SymbolSubscription` instead of the handler holding one anonymously — an ownership change, not a behavior change, since a Session's lifetime already equals its connection's.
- **Execution workflows** (#27, PR #80): `CREATE_TRADE` no longer executes immediately. It validates and prices a trade, holds it as a `PendingTrade`, and replies `TRADE_PENDING` to the submitter only; `CONFIRM_TRADE`/`CANCEL_TRADE` resolve it (confirm still broadcasts `TRADE_CREATED`; cancel replies with a targeted `TRADE_CANCELLED`). `PriceGrid` gained the confirm/cancel prompt UI. ADR 0018.
- **Audit events** (#28, PR #81): a new `AuditEvent` persisted to a new `audit_events` table for `LOGIN_SUCCESS`/`LOGIN_FAILURE`, `SESSION_STARTED`, and terminal trading outcomes (`TRADE_EXECUTED`/`TRADE_CANCELLED`/`TRADE_REJECTED`) — backend-only, no query envelope or UI yet. ADR 0019.

Issues #24, #27, and #28 all left real scope decisions open (auth's protocol shape/credential source/framework choice; execution workflow shape; audit storage/exposure) rather than fully specifying them — each was flagged to @liccioni via `AskUserQuestion` before implementation, per this project's established convention.

## Verified

- Backend: `./gradlew clean test integrationTest` from a clean `main`, no cache — all unit and integration tests passing, including a real Postgres round-trip for the new `AuditEvent` (`AuditEventRepositoryIT`), proactively given the same `Persistable`/app-assigned-id treatment MVP 0.4's `Trade` needed after it silently failed without it.
- Frontend: `npm run test:unit` (29 tests) and `npm run test:integration` (1 test) from a clean `main` — all passing.
- Live, through **both** documented run paths, walking the full milestone story end to end in one pass after the last PR merged (not just per-issue): rebuilt both Docker images fresh and confirmed a `POST /login` with wrong credentials is rejected (401, and produces a `LOGIN_FAILURE` audit row); logged in in the browser and got a personalized greeting; confirmed price ticks stream after subscription; submitted a trade and both confirmed one (executed, appeared in the blotter) and cancelled another (cleared, no blotter row); queried `audit_events` directly via `psql` and found `LOGIN_SUCCESS`/`LOGIN_FAILURE`, four `SESSION_STARTED` rows (one per this app's four independent WebSocket connections), `TRADE_EXECUTED`, and `TRADE_CANCELLED`, all with correct session-id/username attribution. Repeated the login-and-trade portion against the native `gradlew bootRun` + `npm run dev` path (Postgres still via Docker Compose) and confirmed it shares the same blotter/audit history as the Docker Compose path.

## Bugs and gotchas found

No new production bugs this milestone. Worth noting as a positive signal rather than a gotcha: `AuditEvent` got the `Persistable<String>`/`isNew()=true` treatment applied proactively (its id is app-assigned, exactly the shape that silently persisted nothing for `Trade` in MVP 0.4) — the existing [docs/testing.md](../testing.md) gotcha did its job, and the new `AuditEventRepositoryIT` still exists to prove the round-trip rather than trust the pattern blindly.

The one recurring operational pattern (not a project bug) is captured below under New skill candidates.

## Deviations from plan

- **#69, a milestone-less backlog issue, was pulled forward and shipped between #25 and #26.** Its own issue body said it "sets up #26 cleanly," and implementing #26 without it first would have meant either duplicating the same extraction inline inside #26's PR or leaving business logic in the transport layer against `docs/architecture.md`'s own principle. Not a scope change to #26 itself — just a sequencing call.
- **Issues #27 and #28 were both open-ended by design** ("e.g." examples rather than a spec). Two real alternatives raised during #27's scoping — simulated execution venues, and cancelling pending trades on connection close — were ones @liccioni wants to keep exploring later, so they're captured as milestone-less backlog issues (#78, #79) rather than only living in ADR 0018's prose.
- No other structural deviations from the roadmap.

## New skill candidates surfaced

- **Browser-automation live-verification: first interaction after a fresh cache-busted navigation silently no-ops.** Hit on essentially every live-verification pass this milestone (issues #24, #27, and this retro's own final walkthrough): typing into a freshly-loaded page's first field sometimes does nothing because React hasn't finished mounting yet, and the fix is always the same — retry the identical click/type sequence once a screenshot confirms real content rendered. Stable and mechanical enough that `ship-issue`'s live-verification step could just say so up front and save a wasted round-trip every time it happens, rather than rediscovering it per issue.
