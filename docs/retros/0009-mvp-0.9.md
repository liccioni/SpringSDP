## Bugs and gotchas found

- **The audit trail and the `HELLO` greeting record the Keycloak ID token's `sub` claim (a UUID) instead of the username**, everywhere `Session.username()`/`principal.getName()` is used — confirmed both in the UI (`"Hello, d90fe3a3-...!"` instead of `"Hello, trader1!"`) and directly in the `audit_events` table (`LOGIN_SUCCESS`/`SESSION_STARTED`/`TRADE_EXECUTED`/`TRADE_REJECTED`/`LOGOUT` rows all carry the UUID). Root cause: `KeycloakRealmRoleOidcUserService` (added by #117) constructs a `DefaultOidcUser` without a name-attribute key, so `getName()` falls back to `sub`; `application.yml`'s `user-name-attribute: preferred_username` is silently ignored for OIDC logins (it only applies to the plain `DefaultOAuth2UserService` path). Not visible to any test, for the same reason ADR 0025 already flags for the roles bug: tests construct `Session`/`TradeCommand` directly, bypassing the real OIDC token path. Filed as [#127](https://github.com/liccioni/SpringSDP/issues/127) rather than fixed here — tangential to both #117 and #118's actual scope, same treatment PR #124 gave #126.
- **Reusing a session cookie across a gateway process swap can enter an infinite OAuth2 redirect loop.** Found while exercising the README's "Without Docker" path with a browser tab still holding a session from a prior Docker Compose run: every `GET /ws` failed with `IllegalStateException: Session was invalidated` (`ReactiveRedisSessionRepository`), the frontend treated that as unauthenticated and redirected to Keycloak, Keycloak's still-live SSO session silently re-authenticated and bounced straight back, and the new session failed the same way — repeating indefinitely. Not reproduced on a clean `docker compose restart gateway` immediately after, so this isn't "any gateway restart breaks sessions" — narrower and not fully root-caused. Filed as [#128](https://github.com/liccioni/SpringSDP/issues/128); not fixed here, and not required to confirm MVP 0.9's own story (role enforcement and the blotter), which both held up on the Docker Compose path.
- Confirms, a second time, ADR 0025's existing Consequences bullet: **the Keycloak `roles` client scope only puts `realm_access.roles` on the access token by default**, not the ID token — this was already found and fixed as part of #117/PR #124 (an explicit `protocolMappers` entry on `sdp-backend`), and held up correctly on re-verification here.

## Deviations from plan

None structural — both issues shipped matching PR #124's ADR (0025) and PR #125's stated scope. The deviation was in this retro's own verification: the native "Without Docker" path couldn't be fully re-walked due to the session/redirect-loop bug above, so the Docker Compose pass is this retro's primary evidence for both issues' stories holding up end to end.

## New skill candidates surfaced

No new skill. One reinforcement of an existing lesson: retro 0008 already noted that skipping the native "Without Docker" verification pass is exactly what lets path-specific bugs go undetected — this retro hit a *different* native-path bug (#128) than 0008 did (the port-collision one, already fixed), which suggests the native path keeps finding its own class of issue every time it's actually exercised. Worth continuing to run both paths on every future retro rather than treating a clean pass on one as sufficient.
