# Testing

⸻

## Testing stack

### Backend

* JUnit 5
* Reactor Test (StepVerifier)
* Spring WebFlux Test (WebTestClient)
* Testcontainers — adopted in MVP 0.4 (issue #34), see [ADR 0002](decisions/0002-containerization-and-testcontainers.md); backend integration tests needing a real database implement `PostgresIntegrationTest`, a real Redis-backed session implement `RedisIntegrationTest`, and (as of issue #90) a real RabbitMQ broker implement `RabbitMqIntegrationTest`

### Frontend

* Vitest
* React Testing Library
* mock-socket — for simulating the backend WebSocket in integration tests

⸻

## Test levels

Two tiers, for both backend and frontend:

* **Unit tests** — isolated, no Spring context / no real DOM dependencies beyond a component under test. Fast, run on every change.
  * Backend: JUnit 5 tests without the `integration` tag, run via the Gradle `test` task.
  * Frontend: Vitest files matching `*.test.ts(x)`, excluding `*.integration.test.ts(x)`, run via `npm run test:unit`.
* **Integration tests** — exercise real wiring across a boundary (WebFlux/WebSocket endpoints, real component trees).
  * Backend: JUnit 5 tests tagged `@Tag("integration")`, run via the Gradle `integrationTest` task. Tests that need real infrastructure (starting with PostgreSQL from MVP 0.4) use Testcontainers rather than mocks. GitHub Actions' `ubuntu-latest` runners have Docker preinstalled, so this needs no CI workflow changes.
  * Frontend: Vitest files matching `*.integration.test.ts(x)`, run via `npm run test:integration`.

There is no end-to-end tier yet. Add one only when there's a real UI worth exercising that way.

⸻

## Code coverage

Coverage is measured and reported on every PR (Jacoco for the backend, Vitest's `v8` coverage provider for the frontend), and uploaded as a CI artifact. It is not gated — CI does not fail on low coverage. Revisit this once the codebase and test suite are established.

## Known gotchas

* **mock-socket state can leak across tests in the same file.** Sequential tests that each create their own `Server`/`WebSocket` mock against the same URL can interfere with each other if they reuse identical fixture data (the same symbol *and* the same price/payload) — a later test can end up observing a message sent by an earlier test's server. This isn't a bug to work around with extra synchronization; give each test in a file distinct fixture values instead of realistic-looking shared constants, and the tests stay independent.
* **Rendered components don't unmount between frontend tests.** Vitest's `globals` option is off (see `vite.config.ts`), so React Testing Library's automatic `afterEach(cleanup)` registration never fires — it only self-registers when it detects a global `afterEach`. Every earlier test's `render()` output stays in the DOM for the rest of that file. This was invisible until a component introduced a stable `id`/label (`PriceGrid`'s quantity input): a later test's `getByLabelText` silently resolved to an *earlier* test's stale element instead of its own render, because duplicate ids all point at the first match. `src/setupTests.ts` now explicitly imports `afterEach` from `vitest` and calls Testing Library's `cleanup()` — don't remove it, and don't rely on per-file `afterEach(cleanup)` calls instead, since the global one already covers every file.
* **`Sinks.Many#tryEmitNext` requires the caller to serialize concurrent producers, and fails silently if you don't.** Reactor's contract is that `onNext`-equivalent signals must not be concurrent; a `Sinks.Many` doesn't enforce this for you, it detects the violation and returns `FAIL_NON_SERIALIZED` from `tryEmitNext` — which is easy to never notice, since nothing throws unless you check the returned `EmitResult`. `EventBus` had exactly this bug from MVP 0.1 onward (fixed in issue #20): `MarketDataService` publishes from its own ticker thread while `TradeService` publishes from whichever WebSocket connection thread handled a `CREATE_TRADE`, so concurrent `publish()` calls were the normal case, not an edge case, and events were being dropped under real concurrent load. A single-threaded test suite won't catch this — proving it (and proving a fix) needs a test that actually races multiple threads against the sink, e.g. an `ExecutorService` with N producer threads gated by a `CountDownLatch`, publishing simultaneously, then asserting every event arrived (see `EventBusTest`). Any new `Sinks`-backed state fed from more than one thread needs either the same external-synchronization treatment or this style of test proving it doesn't need it.
* **`PostgresIntegrationTest`'s container — and the data in it — is shared across every test method and test class in the same run**, by design (starting one Postgres per test class would be far slower). This means a test can't assume the `trades` table is empty at the start, or that it's the only test that will ever write to it: assert that *your* data is present (`assertThat(history).anySatisfy(...)` or similar), not that the table contains exactly what you put there. This mirrors the mock-socket gotcha above in spirit — shared fixture state across tests — but here the shared thing is a real database table, not a mock server.
* **A Spring Data R2DBC entity with an app-assigned (not DB-generated) `@Id` silently persists nothing unless it implements `Persistable` with `isNew()` returning `true`.** Spring Data's default "is this new?" check is "is the id field null" — since `Trade.id` is a UUID assigned in Java before `save()` is ever called, the id is never null, so the default check assumes the row already exists and issues an `UPDATE` instead of an `INSERT`. The `UPDATE`'s `WHERE id = ...` matches zero rows, which isn't an error — R2DBC just reports zero rows affected — and `save()` still returns the entity you gave it, as if it worked. Nothing is actually in the table. This was invisible until a read query (`findAllByOrderByTimestampAsc`) came up empty right after a "successful" save in the same test. Caught by writing a StepVerifier against the actual repository directly (`save()` then immediately `findById()`) rather than trusting `save()`'s return value alone. Any future entity with an app-assigned id needs the same `Persistable<ID>` treatment (see `Trade`) — or a repository test proving round-trip read-after-write actually works.
* **A `@PostConstruct` method can fire real work before Spring Cloud Stream's messaging channels are marked "running", and the resulting send is silently dropped, not an error.** `market-data-service`'s `MarketDataService` (issue #90) subscribed to its `Flux.interval`-driven tick generator from `@PostConstruct`, exactly as the monolith's old in-process generator always had — safe for publishing to an `EventBus` (a plain in-process `Sinks.Many`), but not for `StreamBridge.send(...)`: Spring Integration's messaging channels aren't marked "running" until *after* every bean's `@PostConstruct`/`afterPropertiesSet()` completes, and `Flux.interval`'s first tick can fire before that — especially with a short interval (1s) against a Spring Boot startup that takes several seconds end to end (Spring Cloud Stream's binder connecting to RabbitMQ, declaring exchanges/queues). The dropped message never throws — Reactor's default `onErrorDropped` just logs it — so nothing fails, a message is simply gone. Invisible in both the unit test (mocked `StreamBridge`, no real messaging channel to be "not running") and the Testcontainers integration test (fast enough in practice not to lose the race); only surfaced live, in `docker compose up` logs, as an `ErrorCallbackNotImplemented` around `MessageDispatchingException: The application context is not ready...`. Fixed by starting on `@EventListener(ApplicationReadyEvent.class)` instead of `@PostConstruct` — the standard Spring Boot signal that the whole context, including messaging infra, is actually up. Any future service that starts pushing to a `StreamBridge`/messaging channel from its own timer or generator needs the same treatment, not `@PostConstruct`.
* **Spring Boot's default component/repository scanning only looks at the main class's own package and its children — a sibling package is silently invisible.** `trading-service`'s `TradingServiceApplication` lives in `com.sdp.trading`; when `com.sdp.audit` (issue #91's `AuditService`/`AuditEventRepository`, moved out of the monolith with the same package name) was added as a sibling rather than a child package, the plain unit test (`@SpringBootTest`, no real infra) failed context startup with `NoSuchBeanDefinitionException: No qualifying bean of type 'com.sdp.audit.AuditService'` — not a wiring typo, just Spring never looking there. The monolith never hits this, since `SdpApplication` sits at `com.sdp`, the common parent of every package it owns. Fixed with explicit `@ComponentScan(basePackages = {"com.sdp.trading", "com.sdp.audit"})` **and** `@EnableR2dbcRepositories(basePackages = {...})` on the application class — the two scan independently (component scanning covers `@Service`/`@Repository`-annotated classes; R2DBC repository scanning covers plain `ReactiveCrudRepository` interfaces, which carry no annotation of their own), so a fix that only adds one silently leaves the other's beans missing. Any future service that splits a package across a sibling boundary like this needs both.
* **An `autoDelete` test-declared RabbitMQ queue can vanish between two `RabbitTemplate.receive(queue, timeout)` calls on the same queue, not just after the test ends.** `trading-service`'s `TradeServiceIT` (issue #91) bound a `new Queue("", false, true, true)` (non-durable, exclusive, auto-delete) per fanout exchange and received exactly one message per test - fine, since the queue only needed to survive one receive. Issue #92 added tests that receive *multiple* messages from the same bound queue (e.g. a `TRADE_PENDING` reply, then later a `TRADE_CANCELLED` reply on the same `trade-responses` queue), and started failing with `NOT_FOUND - no queue 'amq.gen-...'` on the second receive. Cause: `receive(queue, timeout)` isn't a plain poll - it briefly subscribes a real consumer and cancels it once a message arrives or the timeout elapses, and an `autoDelete` queue is removed the instant its consumer count returns to zero, which happens after every single receive, not just at test teardown. Fixed by declaring the queue non-auto-delete and deleting it explicitly in `@AfterEach` instead - `amqpAdmin.deleteQueue(queueName)`.
* **This RabbitMQ version rejects declaring a queue that's both non-durable and non-exclusive outright**, as a side effect of the fix above: swapping `autoDelete` from `true` to `false` while leaving `exclusive` at `false` too produces `INTERNAL_ERROR - Feature 'transient_nonexcl_queues' is deprecated... not permitted anymore` and closes the connection. The fix for the auto-delete gotcha above needs `exclusive: true` specifically (`new Queue("", false, true, false)` - non-durable, exclusive, not auto-delete), not just "auto-delete off" - exclusive ties the queue to the test JVM's own long-lived shared connection instead of to any single `receive()` call, which is also what keeps it alive across multiple receives.
* **One bad or slow WebSocket message can silently kill the whole connection, and nothing in a single-threaded test catches it.** `SdpWebSocketHandler.handleIncoming`'s `flatMap` used to let a per-message error (malformed JSON, or a downstream reply that times out) propagate all the way up and terminate the connection's own `inbound` Flux — no error surfaced to the client, no reconnect, the socket just went silently dead. Found live-testing issue #131 (MVP 1.0): `TradeBlotter.tsx`'s `GET_TRADE_HISTORY` request timed out after 10s (`trading-service` NPE'd on a still-missing payload, a gap already deferred to #132), and that `TimeoutException` closed the connection outright — looked exactly like a filter bug in the blotter, but was actually the connection dying ~10s after every page load. Fixed (issue #140) by wrapping each message in `Mono.defer(...)` (so a synchronous throw becomes a proper error signal too, not just async ones) and `.onErrorResume(...)` (logs a warning, resolves to empty instead of propagating) inside a new `handleOneMessage`. The fastest regression test doesn't need to wait out a real timeout: send malformed JSON over a real connection, then a normal `CREATE_TRADE`, and assert the reply still comes back — proving the connection survived the bad message (see `aMalformedIncomingMessageDoesNotCloseTheConnection`). Any future per-message handling in `SdpWebSocketHandler` needs the same error boundary — a `CREATE_TRADE`/`CONFIRM_TRADE`/`CANCEL_TRADE` round-trip timing out against a slow/unavailable service is just as capable of triggering this as `GET_TRADE_HISTORY` was.
* **`@Container`-managed static Testcontainers fields only share a container within one test class, not across a whole run.** `trading-service`'s `PostgresIntegrationTest`/`RabbitMqIntegrationTest` looked identical to backend's (a `static` field annotated `@Container @ServiceConnection`, documented above as shared "across every test method and test class in the same run"), but that claim was only ever true by accident: each module had exactly *one* real `@Tag("integration")` class touching RabbitMQ (`TradeServiceIT`), so the JUnit5 Testcontainers extension's actual behavior - starting a static container once, then **stopping it after the last test method of the class that happens to run it**, not at JVM shutdown - never got exercised. Issue #93 added a second such class (`AuditServiceIT`), and whichever one ran second started failing every test with `AmqpConnectException: Connection refused`, even though a fresh container demonstrably got created (visible in the logs) - because the *Spring test context* is cached and shared across both classes (both resolve the same `@SpringBootConfiguration`), so it kept the **first** container's now-dead host:port rather than picking up the new one. Fixed in `trading-service`'s own copies of both interfaces (not backend's or `market-data-service`'s, since neither has hit this yet) by switching to Testcontainers' documented "singleton container" pattern: a plain field (no `@Container`, no `@Testcontainers`) started once via a small static helper method, relying on Ryuk rather than the extension for cleanup at JVM exit. Any module that grows a second real integration test class sharing a Testcontainers-backed resource needs the same treatment.
